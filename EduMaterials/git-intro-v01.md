# Памятка по работе с ветками и задачами (Jira, Confluence, GitHub)

Документ описывает базовый процесс работы с кодом через связку Jira (задачи), GitHub (хранение кода) и Confluence (документация). Шаги изложены последовательно.

---

## Предварительная настройка (однократно)

### Настройка Git

Укажите ваше имя и email — они будут отображаться в истории коммитов:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "your.email@example.com"
```

Проверьте настройки:

```bash
git config --list
```

### Файл .gitignore

Файл `.gitignore` указывает Git, какие файлы НЕ нужно отслеживать. Типичные исключения:

- Логи (`*.log`)
- Временные файлы (`*.tmp`, `*.swp`)
- Зависимости (`node_modules/`, `venv/`)
- Конфигурации с секретами (`.env`, `credentials.json`)
- Скомпилированные файлы (`*.pyc`, `*.class`, `build/`)

Убедитесь, что в проекте есть `.gitignore` перед первым коммитом.

## Шаги рабочего процесса

### Шаг 0. Настройка SSH-ключей (однократно)

SSH-ключ необходим для безопасного доступа к GitHub без повторного ввода пароля. Подробная официальная инструкция по генерации и добавлению ключа:

[GitHub Docs: Connecting to GitHub with SSH](https://docs.github.com/en/authentication/connecting-to-github-with-ssh)

Кратко: сгенерируйте ключ, добавьте публичную часть в настройках GitHub (Settings → SSH and GPG keys). После этого локальный компьютер сможет обмениваться данными с GitHub.

### Шаг 1. Клонирование репозитория по SSH

Клонирование — это создание локальной копии удалённого репозитория.

На странице репозитория на GitHub нажмите кнопку **Code**, выберите вкладку **SSH** и скопируйте URL.

В терминале перейдите в нужную директорию и выполните:

```bash
git clone git@github.com:username/repository.git
```

Перейдите в скопированную папку:

```bash
cd repository
```

Теперь у вас есть локальная рабочая копия проекта.

### Шаг 2. Создание задачи в Jira

Задача описывает требуемое изменение в проекте.

1. Откройте Jira, выберите проект.
2. Нажмите **Create** (Создать).
3. Заполните поля:
   - **Summary** — краткое название задачи.
   - **Description** — подробное описание.
4. Сохраните задачу и запомните её номер (например, `PROJ-123`) — он понадобится для имени ветки.

### Шаг 3. Создание ветки на GitHub

Ветка позволяет изолировать изменения по задаче, не затрагивая основную ветку (`master`).

1. На странице репозитория на GitHub откройте список веток.
2. Введите имя новой ветки. В имени ветки обязательно должна присутствовать подстрока с номером задачи (например, `PROJ-123`), чтобы связка между Jira и GitHub работала корректно. Рекомендуемый формат: `PROJ-123-краткое-описание`.
3. Нажмите **Create branch**.

Ветка создана на GitHub («внешняя ветка»).

### Шаг 4. Получение актуального состояния и переключение на ветку

Необходимо получить свежую информацию о ветках и создать локальную ветку, связанную с внешней.

Обновите информацию о ветках с удалённого репозитория:

```bash
git fetch origin
```

Посмотрите список локальных веток:

```bash
git branch
```

Посмотрите список внешних (удалённых) веток:

```bash
git branch -r
```

Создайте и переключитесь на локальную ветку, отслеживающую внешнюю:

```bash
git checkout -b PROJ-123-краткое-описание origin/PROJ-123-краткое-описание
```

Если после переключения вы обнаружили, что внешняя ветка была изменена (например, коллеги запушили новые коммиты), выполните команду для получения актуальных изменений:

```bash
git pull
```

Эта команда получит изменения с удалённой ветки и объединит их с вашей локальной веткой.

Теперь все изменения будут вноситься в эту ветку, а не в `master`.

### Шаг 5. Внесение изменений

Откройте проект в редакторе кода и выполните необходимые правки согласно задаче. Сохраните файлы.

### Шаг 5.5. Проверка изменений перед коммитом

Перед коммитом проверьте, что именно изменилось:

```bash
git status              # список изменённых файлов
git diff                # подробные изменения в файлах
git diff --stat         # краткая статистика изменений
```

Убедитесь, что не коммитите лишние файлы (логи, временные файлы, секреты, настройки IDE).

### Шаг 6. Добавление в индекс и коммит

Коммит фиксирует изменения с описанием.

Проверьте статус изменённых файлов:

```bash
git status
```

Добавьте файлы в индекс:

```bash
git add .
```

Создайте коммит:

```bash
git commit -m "PROJ-123: краткое описание изменений"
```

**Совет по сообщениям коммитов:**

Пишите осмысленные сообщения коммитов:

- ✅ Хорошо: `PROJ-123: добавить валидацию email в форме регистрации`
- ❌ Плохо: `fix`, `update`, `changes`, `wip`

Сообщение должно отвечать на вопрос «что сделано и зачем».

### Шаг 7. Отправка изменений на GitHub (push)

Отправьте локальные коммиты в удалённую ветку:

```bash
git push
```

Если ветка уже связана с внешней, команда выполнит отправку. При необходимости git подскажет уточнённую команду.

### Шаг 7.5. Разрешение конфликтов слияния (при необходимости)

Если при `git pull` или `git merge` возник конфликт:

1. Git покажет файлы с конфликтами.
2. Откройте эти файлы в редакторе.
3. Найдите маркеры конфликта:

```
<<<<<<< HEAD
ваш код
=======
код из другой ветки
>>>>>>> branch-name
```

4. Выберите нужный вариант или объедините оба.
5. Удалите маркеры конфликта.
6. Добавьте исправленные файлы:

```bash
git add имя-файла
```

7. Завершите слияние:

```bash
git commit
```

### Шаг 8. Создание Pull Request

Pull Request (PR) — запрос на включение изменений из вашей ветки в основную ветку (`master`).

1. Откройте репозиторий на GitHub.
2. Нажмите **Pull requests** → **New pull request**.
3. Выберите **base**: `master`, **compare**: `PROJ-123-краткое-описание`.
4. Проверьте изменения, добавьте описание (можно сослаться на задачу в Jira).
5. Нажмите **Create pull request**.

**Рекомендации по Code Review:**

- Добавьте понятное описание изменений.
- Укажите связанные задачи Jira.
- Попросите review у конкретных коллег.
- Отвечайте на комментарии вовремя.

После проверки коллегами изменения будут влиты в основную ветку.

### Шаг 9. Документирование в Confluence

После завершения задачи обновите документацию:

1. Откройте Confluence, найдите страницу проекта.
2. Опишите:
   - Что было сделано (кратко).
   - Какие решения приняты и почему.
   - Изменения в архитектуре (если есть).
   - Инструкции по использованию новой функциональности.
3. Добавьте ссылку на PR в GitHub.
4. Сохраните страницу.

Это поможет команде понять контекст принятых решений.

### Шаг 10. Обновление основной ветки после merge

После того как PR одобрен и влит в `master`:

Переключитесь на основную ветку и обновите её:

```bash
git checkout master
git pull
```

Теперь ваша локальная основная ветка содержит актуальные изменения, включая ваши собственные. Можно приступать к следующей задаче.
